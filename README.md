# 环卫线路工作台（封路重排演示）

浏览器端环卫线路工作台：调度员在地图与路线清单中查看道路限行、服务截止、每站估重、车辆载重与卸载点时段；司机按当前线路登记到站/扫码/称重/满溢/封路；客服按线路版本核查预约通知是否仍有效。全部数据为随题固定的虚构数据，存于浏览器 IndexedDB，可一键重置重放；线路重排在 WebWorker 中计算。

## 技术栈

- React 18 + TypeScript + Vite
- IndexedDB（`idb`）：车辆、站点、路网、封闭、卸载点、通知、线路版本、回执、事件日志全量落库
- WebWorker：重排方案（最小变更 / 全局重排）在后台线程计算
- 纯前端，无后端；nginx 托管静态资源（Docker）

## 随题固定的场景

09:20，清运班组长收到通知：**清河桥（S1—S2）09:20–10:15 封闭**，T1 无法按原顺序进入 S2（S2 截止 10:00；绕行最短 42 分钟，10:02 才到，仍超截止）。

- T1：容量 5.0t、已载 3.0t，剩余 S1（估 0.7t）、S2（估 1.2t）
- T2：容量 4.0t、已载 0.8t，原路线 S3（0.8t）→ S4（0.7t），居民已获知预计到达
- S2 截止 10:00，S3 截止 10:30，S4 截止 11:00；卸载点 D1 开放 08:00–12:00
- 道路限制：市场高架（S2↔S4）限高 2.6m（T1 高 3.1m 不可通行）；车场↔S2 限宽 2.5m

点「生成方案」后页面**并列显示两个方案**（不只给一条最优线）：

- **方案 A · 最小变更**：S2 前置移交 T2，其余已通知顺序不变。T2 = S2→S3→S4，行驶 25 分钟（合计 31）；仅 S2 的 1 条通知需重发
- **方案 B · 全局重排**：T2 = S3→S2→S4，行驶 14 分钟（合计 20，省 11 分钟）；但 S2/S3/S4 共 3 条通知需重发（车辆变更、到达提前 10/7 分钟）

两案均通过吨位、限高限宽、截止时刻、卸载点时段核验；被排除候选（如「T1 承运 S2：绕行 10:02 到达，超过截止 10:00」）一并展示——不用“地图上可达”代替限制核验。

登录调度员 `dispatcher/disp123`，右侧「演示与验证」面板可一键注入题目输入；建议流程：

1. **重置并重放**（按钮①）：回到 09:20 封路现场。路线清单中 T1 当前线路显示红色不可行提示
2. **生成两个重排方案**：并列对比路线、载重、延误、需重发通知（见上节数值）。选择**应用方案 B** → 生成 RV-T1-2 / RV-T2-2，S2 移交 T2，3 条通知标记“需重发”
3. 登录客服 `service/svc123`：通知表显示 N2/N3/N4 “需重发”及原因，逐条**重发通知**（按当前版本 RV-T2-2 更新）
4. 登录司机 `driver2/drv123`（T2）：对 S3 依次**到站 → 扫码 → 称重 0.8t**；对 S2 同样操作，**称重时输入 2.4t**（实称 ≠ 估重 1.2t）→ 剩余容量 2.4t 恰好可装，T2 满载 4.0t，页面立即提示“后续 S4 超载，线路不再可行”
5. 小李若继续对 S4 称重 0.7t → **停收/拒收提示**（实称超剩余容量 0t），可尝试“转场卸载”
6. 回到调度员：再次生成方案 → S4 移交 T1（RV-T1-3），N4 需重发；按钮②注入**卸载点提前至 10:00 关闭**（时钟过 09:55 后司机端转场卸载即不可用）
7. 按钮③注入**老王迟到的离线回执**（S2 扫码，依据旧版本 RV-T1-1）→ 判定**冲突**，S2 仍显示“小李完成”，不被改判；再点一次 → **重复**，同一凭证只计一次
8. 登录司机 `driver1/drv123`（T1）：完成 S1（0.7t）、S4（0.7t）
9. 按钮④推进时钟到 10:15，封路解除。最终：S1–S4 全部在截止前完成，通知全部“已履约”，回执流水中冲突/重复各 1 条；调度员与司机、客服均可在「线路版本追溯」中看到 RV-T1-1→RV-T1-3、RV-T2-1→RV-T2-3 的依据链

司机端另可验证：**离线模式**（操作进待上传队列）→「上线并上传」补录生效；**满溢上报**、**封路上报**即时进入调度员视图与事件日志。

## 关键规则实现

- **估重 ≠ 实称**：规划用估重；称重写入实称后，剩余容量不足必须停收并触发重排；已称重站点重排时按实称计算
- **回执幂等**：同一回执号（或同人同站同动作的同一二维码）重传只计一次，判定“重复”
- **迟到回执冲突**：站点已移交他人或已不在该车当前线路版本中 → 旧回执判定“冲突”，不改变站点状态
- **线路版本**：每次应用方案生成新版本（记录策略、原因、依据版本）；回执、通知均关联版本号，司机端与客服端可追溯到当前线路所依据的版本
- **通知重发判定**：承运车辆变更、到达时刻偏移 >5 分钟、同车相对顺序变化 → 需重发
